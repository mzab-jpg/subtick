# Plan: Rebuild `simulator.html` around Config × Persona comparison

## Your locked decisions (recap)
1. **Primary question:** Config comparison — "I have candidate app configs; show me how each performs across user types so I can pick the best."
2. **Framing:** App config stays fixed; user behaviour is the unknown you stress against.
3. **Biggest UX sin:** Results don't compare — every run overwrites the previous.
4. **Comparison unit:** You keep full manual control of every app variable; you test your current config under different **named user scenarios**.
5. **Persona model:** Named user personas (handful), not random distributions.
6. **Persona seed:** I propose **5 grounded personas** (editable).
7. **Layout:** **Tab per config, charts within** — each candidate config is a tab; inside, you see its behaviour across all personas; the tab strip is the comparison axis.

## The core mental model the redesign establishes
- **App Variables** = everything in `getConfig()` that the developer ships (score weights, deltas, learning rates, decay, trending/quality increments, tranche assembly). These live in a clearly-labelled **"App Configuration"** editor.
- **User Variables** = the behaviour assumptions (8 behaviour rates + reading/prefs/consistency). These are now packaged into **named Personas** rather than free-floating mean/stddev fields.
- The old behaviour mean/stddev inputs (lines 79–87, 104–122) become the **persona editor**: instead of one global behaviour block, you maintain a small set of personas. The population-level inputs (numUsers, numDays, feeds, articles) stay as simulation-size controls.
- The simulation runs your **one current App Configuration** against **all enabled personas in parallel**, then stores the result as a new **config tab**. Flip tabs to compare.

### How a run works now
1. You set your App Configuration (left pane) — exactly as today.
2. You pick which personas are enabled (checkboxes, default all 5) and the simulation size.
3. Click **"▶ Run & Save as Config Tab"**.
4. The engine runs **N parallel simulations** (one per enabled persona), each using the SAME app config but that persona's behaviour profile. Implementation: reuse the existing `runSimulation` core, but loop over personas, swapping `config.behaviour` + `config.reading` + `config.prefs` + `config.consist` per iteration.
5. Each persona run produces the full `simData` structure (dailyMetrics, users, articles, etc.).
6. The combined result `{configName, appConfig snapshot, personaResults: {Engaged: simData, Casual: simData, ...}}` is pushed onto a **`configTabs[]` array** and a new tab is rendered.
7. The first tab is auto-named "Config 1"; subsequent runs auto-increment. A pencil icon lets you rename. A "tag" shows which app variables differ from the previous tab (e.g. "P: 0.60→0.50").

### What's inside a config tab (the comparison view you asked for)
Two modes, toggled within the tab:

**Mode A — Persona Comparison (default):** The headline answer. A grid where **columns = personas, rows = key metrics** (avgP final, P-dominant %, avgFS, high-tranche %, feed diversity, weight spread), cells color-coded green(best)→red(worst) **per metric row**. This is the at-a-glance "does my config hold up across user types?" view. Plus a small **per-persona metric sparkline row** so you see trajectory, not just endpoint.

**Mode B — Persona Detail:** Select one persona → see that persona's full chart suite (the existing 14 charts: P-score distribution, dominant shift, weight spread, tranche breakdown, per-user P distribution, etc.). This preserves all the rich per-simulation visualization that already works; it's just scoped to one persona within this config.

### The cross-tab comparison (the real payoff)
Because every tab stores its app-config snapshot + all persona results, a **"Compare" overlay** (button on the tab strip) renders a single grid: **rows = (persona × metric), columns = config tabs**. This directly answers "config v1 vs v2 vs v3, each across all personas" — flip the question: instead of flipping tabs and memorizing, you see them side by side. Cells color-coded per row so the best config per persona-metric jumps out. This is the "results don't compare" sin fully fixed.

- CSS: tab strip, persona grid, color-coded cells, overlay. Added to existing `<style>` block; existing palette kept.

### Behaviour note on multi-persona runtime
Running 5 personas × (e.g.) 1000 users × 14 days each is ~5× the current single-run cost. The existing `setTimeout(processDay,0)` async pattern keeps the UI responsive per persona; personas run sequentially (persona 1 fully, then persona 2, …) with a combined progress bar ("Persona 2/5 — Day 7/14…"). A "fast mode" checkbox (default on for comparison runs) caps users to 200 and days to 7 per persona for speed, matching what `runQuickSim` already proved fast enough.

## What this delivers against your complaint
- *"Ability to simultaneously test across user variables is rubbish"* → now you test across **5 named personas in one run**, results in one grid, instead of one randomized blob.
- *"UI positioning is terrible"* → three-pane layout with clear labels: App Config (what I configure) / Personas (what I assume about users) / Config Tabs (the comparisons I've built).
- *"Can't see how app variables function considering user variables"* → the Persona Comparison grid shows, per config, exactly how each app setting plays out per user type; the Compare overlay shows it across configs.
- *"Eventually 10s of configurations"* → tabs + the Compare overlay scale to many configs; personas stay a fixed handful (5, expandable) so the comparison grid never explodes.
- *"Results don't compare"* → fully fixed: nothing is overwritten; every run is a new tab; side-by-side compare overlay.
